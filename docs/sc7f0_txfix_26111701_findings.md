# 26111701 TX/capture diagnosis — what the four blockers actually are

Date: 2026-11-17. Card state at start: `0x26111602` running, host `qpcie.ko` loaded,
HDMI source connected **for this round** (the operator attached the monitor).

Everything below is measured. Evidence paths are under `build/txfix-26111701/` (this
round) and `build/accept-26111602/` (the previous round's baseline). No COMMIT was run;
nothing on the card was made persistent; no commit/push in git.

---

## 1. TX HPD is not broken — it was measured before the cable was attached

`build/txfix-26111701/card-hpd-now.txt`, ten seconds of sampling plus the subsystem's own
view:

| Signal | Where | Value |
|---|---|---|
| raw sink HPD pin | `0xA00006A0` bit10 (`u_hdmi_probe`, 3-stage ASYNC_REG on `hdmi_tx_hpd_in`, pin G14) | **1** |
| TX subsystem HPD input | `0xB0020064` (`S_AXI_CPU_IN` +0x64, `XV_HDMITX_PIO_IN_HPD_MASK` = bit2) | `0x804` → **bit2 = 1** |
| connector | `/sys/class/drm/card0-HDMI-A-1/status` | **connected** |
| subsystem IRQ | `/proc/interrupts` line 58 `xilinx-hdmitxss` | 4 (edges did fire) |

The `HPD = 0` reading in `build/accept-26111602/` was taken at 06:31, before the monitor was
connected; bit10 of the same register read `0x3F03F8AF` then and `0xAF03FCAF` now, the
difference being exactly bit10. XDC (`constraints/zu4ev_pcie_pinout.xdc:69`, `G14`,
`LVCMOS33`, input, plus the false-path to `u_hdmi_probe/tx_hpd_sync_reg[0]`) and the top-level
wiring `.hpd(hdmi_tx_hpd_in)` are both correct, so **no RTL/XDC change was made for HPD and
none is needed.** Note that `0x800` in the old `PIO_IN` reading is `BRDG_UNDERFLOW`, not HPD —
that misreading is what made blocker #1 look real.

## 2. The display blocker is DDC/EDID: the design contains no I2C master

With HPD high the connector reports `connected` but has **zero modes** and
`edid` = 0 bytes. The reason is structural:

* `grep -n "iic\|i2c" scripts/create_zu4ev_ps_bd.tcl` → **no matches**: the SC7F0 PS block
  design has no I2C controller at all.
* The only I2C in the live tree is the PS's own `ff030000` (`i2c-0`, "Cadence I2C at
  ff030000") whose clients are `0-0032` (NUC1262) and `0-0068`. `i2c@ff020000` is
  `status = "disabled"`. There is **no second host adapter**
  (`build/txfix-26111701/card-ddt.txt`), so no `ddc-i2c-bus` can resolve.
* In the fabric, `hdmi_tx_scl`/`hdmi_tx_sda` (T14/U12) are top-level ports that the RTL ties
  high — probe bits 13/12 (`tx_sda`, `tx_scl`) read 1,1 = idle, and nothing drives them.

Proof that this is the missing piece rather than a driver problem: the kernel's EDID
override is consulted *before* any adapter, so a blob can be injected at runtime.

`build/txfix-26111701/card-edid-ovr2.txt` (256-byte blob generated by
`build/txfix-26111701/make_edid.py`, written as **binary** — the hex form returns EINVAL):

```
== before            status=connected modes=0 edid_sysfs=0
== after binary write status=connected edid_sysfs=256        <- the kernel took the blob
```

`modetest -M xlnx -c` then showed the 256-byte EDID attached to the connector's `EDID`
property, and the physical size became `640x350`, i.e. `drm_edid_connector_update()`
parsed my base block. Modes did **not** appear because that blob was rejected:
`[drm] HDMI-A-1: EDID invalid.` (`build/txfix-26111701/card-why-no-modes.txt`). The mode
list visible at that point — `1024x768/800x600/848x480/640x480`, all ≤ 65 MHz — is exactly
`drm_add_modes_noedid()`'s fallback set, which confirms `get_modes()` still returned 0.

So: **HPD fine → EDID impossible → no modes → no modeset.** Two follow-ups:

* the blob itself needs fixing (it is structurally plausible — checksums verified, CTA
  extension with VIC 16/31/94/97, DTD offsets at 54/109 — but the kernel rejected it, and
  the fast path to a working screen is to test with `video=HDMI-A-1:...` on the kernel
  command line, which `drm_helper_probe_single_connector_modes()` honours without an EDID);
* the *real* fix is an I2C master on the DDC pins. The cheapest shape that keeps the
  upstream driver stack is the PS's second I2C (`i2c@ff020000`, currently disabled) routed
  through EMIO to `hdmi_tx_scl`/`hdmi_tx_sda`, with `&hdmi_tx { ddc-i2c-bus = <&i2c0>; }`;
  the alternative is an `axi_iic` in the unused 0xA0007000 slice plus its own DT node and
  IRQ. Either way this needs a PS-BD/fabric change, not a register fix.

## 3. The TX link/video clocks are dead, which is a consequence, not a cause

`build/txfix-26111701/card-txclk2.txt` — the fabric's own clock monitors (probe block base
is `0xA0000600`; `0xA0000080` is a different window and legitimately reads zero, which is
why the first attempt looked like "everything is dead"):

```
probe_version 0xA0000680 = 0x26102201     rx_clk       0xA0000684 = 0x08D9BBA9
rxoutclk      0xA000068C = 0x11B37752     rx_video_clk 0xA0000690 = 0x11B37752
tx_clk        0xA0000694 = 0x00303AA0     txoutclk     0xA0000698 = 0x00000000
                                          tx_video_clk 0xA000069C = 0x00000000
```

`phy_txoutclk`/`phy_tx_video_clk` are the subsystem's `link_clk`/`video_clk`, and they only
run once the VPHY TX link is brought up, which the DRM driver does during a modeset. With
no EDID there is no modeset, so they stay at 0, and the boot-time fbcon mode never
completes a commit: `[drm] *ERROR* flip_done timed out` for `CRTC:34`/`PLANE:32`
(`card-why-no-modes.txt`). This is downstream of §2 and needs no separate fix.

## 4. VTC at 0xB0030000: where the abort does *not* come from

Measured edge, `build/txfix-26111701/card-edge.txt`:

```
0xB002E000 0x22000100   0xB002EC00 0x22000100   0xB002FC00 0x22000100
0xB0030000 ABORT        0xB0030400 ABORT        0xB0030C00 ABORT
afterwards: 0xB0020040 = 0x22000100, 0xA0000680 = 0x26102201   (bus healthy, no latch-up)
```

**Ruled out, with the artifact that rules it out:**

* *"the VTC segment is missing from the subsystem's own map"* — the built IP's handoff says
  otherwise: `bd_0/hw_handoff/v_hdmi_tx_ss_rgb.hwh` contains
  `MEMRANGE BASEVALUE="0x00010000" HIGHVALUE="0x0001FFFF" INSTANCE="v_tc"
  MASTERBUSINTERFACE="S_AXI_CPU_IN" SLAVEBUSINTERFACE="ctrl"`.
* *"the outer crossbar's M10 window is misconfigured"* —
  `scripts/create_sc7f0_hdmi_crossbar.tcl:58` sets `M10_A00_BASE_ADDR 0x00000000B0030000`,
  `M10_A00_ADDR_WIDTH 16`, and the built `.xci`'s generated per-master width word reads
  `…00000010` for M10 (16) and `00000010` for M02, matching.
* *"the RTL slices the flattened address vector wrong"* — the IP's own stub declares
  `m_axi_araddr[351:0]` (`axi_crossbar_hdmi_stub.v`, 11 masters × 32 bits), so
  `hdmi_ctl_araddr[335:320]` (M10) and `[79:64]` (M02) in
  `rtl/zu4ev_pcie_card_top.v:1790,1808` are the correct fields.
* *"`sc7f0_axil_merge_2to1` forgets the address prefix"* — the prefix is supplied at the
  instantiation: `.s0_axil_araddr({1'b0, hdmi_ctl_araddr[79:64]})`,
  `.s1_axil_araddr({1'b1, hdmi_ctl_araddr[335:320]})`, and the module muxes the selected
  slice's address straight through, so a granted S1 read presents bit16 = 1.
* *"the VTC registers are simply unreachable in principle"* — a delivered-but-wrong address
  cannot produce this abort. `v_hdmi_tx`'s control slave is 9 bits, which is why
  `0xB002C000`, `0xB002E000`, `0xB002F000` **all read `0x22000100`**: bits above [8] are not
  forwarded and the TX core answers with aliasing. **The "lower window aliases to
  0x22000100" observation from the previous round is normal behaviour, not a defect** — that
  misreading is what pointed the last two rounds at the address map. Anything delivered to
  the subsystem would have been answered by the TX core; a fast DECERR that leaves the rest
  of the bus working means the request never reached the subsystem's control port.

**Still open:** which decoder rejects it. The same HPM path answers `0xB0040000`
(`0x44505631`), `0xB0090000` (`4`) and `0xB00A0000` (`0x100`), so the path is alive; the
failure begins at the M10 slice boundary and the abort is DECERR-class rather than a hang.
The next round should settle it with an authoritative address report of the *linked, built*
design (`report_ip_address_assignments` / `report_connectivity` on the pre-`opt_design`
checkpoint, since `u_hdmi_control` and the merge cell are merged by `opt_design` and the
routed names mislead — see `probe-preopt-connect.tcl`), plus a gate-level run of the built
top netlist driving `0xB0030000` against a slave model that answers DECERR for the
subsystem's hole (`0x1000..0xFFFF`), because a model that always answers OKAY cannot see
this class of bug.

## 5. Fixed this round: the host driver's overlay version gate

`driver/qpcie_overlay.c` refused to open `/dev/qpcie-ovl-*` unless the fabric reported the
exact literal `0x26111503`. It now admits a card on either of two independent grounds:

```c
#define QOVL_HW_VERSION_FLOOR 0x26111503U
...
if (!(caps & QPCIE_CAP_RGB_COMPOSITOR) && ver < QOVL_HW_VERSION_FLOOR)
        → refuse, and say which of the two it checked
```

so capability is authoritative when the fabric publishes it, and the floor keeps older
images working. The capability bit is now real on both sides:

* `driver/qpcie_driver.h`: `QPCIE_CAP_RGB_COMPOSITOR BIT(20)`;
* `rtl/axil_reg_space.v`: `HARDWARE_CAPS_VAL = SC7F0_C2H_CAPS_BASE | 32'h0010_0000` under
  `` `ifdef SC7F0_RGB_COMPOSITOR `` — the RGB persona adds the bit, a plain C2H card does
  not, so the driver can tell the two personalities apart without matching a version;
* `tb/sc7f0_c2h_caps_tb.sv` checks both `0x1001_011F` and `0x1011_011F`, and
  `scripts/tests/test_sc7f0_c2h_profile.py` now compiles the TB **both ways**
  (4 tests OK), which is what makes a silent capability regression a test failure.

## 7. Consequences for building 26111701

The fabric delta is one capability-bit line plus a version bump. That build can deliver
acceptance for §5 and §6, and re-test host C2H RGB888 4K60. **It cannot deliver the HDMI-TX
half of the acceptance list**, because §2 (no DDC master → no EDID → no modes → no
modeset) is a design gap that an address-map or driver change does not touch. Building and
flashing 26111701 without closing §2 would burn the round's single COMMIT on a build that
cannot pass, so the DDC decision comes first:

1. close §2 properly (PS I2C0 via EMIO → DDC pins + `ddc-i2c-bus`, or `axi_iic` at
   0xA0007000) — real EDID, real modes, then VPHY clocks, then re-test `0xB0030000`; or
2. ship a `video=HDMI-A-1:…` cmdline override as a bring-up measure (no EDID, forced mode)
   and accept a connector with one synthetic mode; or
3. build 26111701 now as `BRINGUP_ONLY_NOT_RELEASE_ACCEPTED` carrying §5/§6 only.

Runtime state left on the card: the injected EDID override and the forced connector state
were both cleared; both were debugfs-only and a reboot clears them regardless. No file on
the card was created or modified, and nothing outside `/tmp` (tmpfs) was written.

## 8. 2026-11-17 re-measurement on deployed `26111602` — §2 is closed, §3 is not

All of §2 ("no DDC master → no EDID → no modes") was an artefact of stale runtime state,
not a design gap. Re-measured on the deployed card with read-only + debugfs-only actions.

### 8.1 HDMI-TX DDC/EDID works today; no PS I2C0, no `ddc-i2c-bus`

`build/ddc-vtc-26111701/card-edid-real.sh` (transcript `card-edid-real.txt`):

| step | result |
|---|---|
| `cat /sys/class/drm/card0-HDMI-A-1/edid` | 256 bytes, but the first bytes were the injected block |
| `/sys/kernel/debug/dri/0/HDMI-A-1/edid_override` | **256 bytes — a leftover override from the previous round** |
| `printf reset > .../edid_override` | override length → 0 (an *empty* write does **not** clear it; the token must be exactly `reset`) |
| `modetest -M xlnx -c` (re-probe) | `status=connected`, `edid=256`, `modes=29`, several `3840x2160` entries |

So the connector re-reads a real 256-byte EDID over the HDMI TX **subsystem's own DDC
master** (`v_hdmi_tx_ss/DDC` → `sc7f0_ddc_iobuf` → `hdmi_tx_scl/sda`) and enumerates 4K
modes. TX SS DDC register snapshot in the same transcript: TX ID `0x22010204`,
`DDC_CTRL 0x01F30000` (CLK_DIV=499, written by the driver), `DDC_STA 0x000002C0`.

The reference design agrees — it does not use PS I2C for TX DDC either:

* `~/docker/sc6f0-dante/vivado/dante-rx-v2023.2/dante-rx-v2023.2.tcl` exposes
  `v_hdmi_tx_ss_0/DDC_OUT` as the top-level port `hdmi_tx_ddc_out` (pads, not a PS bus);
* that reference PS BD has **I2C0 disabled** and I2C1 on MIO40..41 for the MCU;
* no `ddc-i2c-bus` and no `axi_iic` anywhere in the dante-rx / dante-tx-v2023-2 device
  trees; their `hdmi.dtsi` only overrides clocks/audio/codec properties.

Conclusion for the plan item "implement PS I2C0 `ff020000` via EMIO + `IOBUF` and/or
`ddc-i2c-bus`": **do not do it.** It would put a second master on the same DDC pins the
subsystem IP already drives (and would collide with nothing else only because I2C0 is
otherwise unused). The existing internal-DDC wiring is correct and demonstrably working;
`rtl/zu4ev_pcie_card_top.v` keeps its `sc7f0_ddc_iobuf` pads unchanged in `26111701`.

### 8.2 The `0xB0030000` VTC abort is immediate refusal, not a timeout

`build/ddc-vtc-26111701/card-vtc-timing.sh` (`card-vtc-timing.txt`), 20 reads each, timed
with `/proc/uptime` (centisecond resolution):

| window | 20 reads | single read |
|---|---|---|
| `0xB0020000` TX core (answers) | 14119.08 → 14119.12 | `0x22000100`, rc=0 |
| `0xB00B0000` **no slice covers it** | 14119.12 → 14119.16 | rc=135 (SIGBUS) |
| `0xB0030000` VTC half | 14119.16 → 14119.20 | rc=135 (SIGBUS) |

Identical cost for all three: 20 reads fit in one 0.04 s bucket, i.e. the whole cost is
`fork`/`exec`. The VTC access is therefore answered **immediately** — it is *not* a slave
that never responds being cut off by a NoC timeout. That rules out the "VTC's `clk` is
`phy_tx_video_clk`, which is 0 Hz until the link trains, so the access stalls" theory as
the explanation of the abort itself (the VTC's `s_axi_aclk` is on the `axi_crossbar/aclk`
= `pl_clk0` net per `v_hdmi_tx_ss_rgb.hwh`; only its `clk` is `video_clk`).

### 8.3 The deployed netlist really does carry the VTC path

`scripts/probe_sc7f0_txss_vtc_path.tcl` against the routed DCP of `26111602`
(`/mnt/data-root/.../rgb-a1b1-26111602-20261116T141240Z`, transcript
`vtc-path-probe.txt`) — the `26111602` fabric merge is present and connected:

* `u_hdmi_control/m_axi_arvalid[2] ↔ u_hdmi_tx_ctl_merge/m_axi_arvalid[0]` (M02 = TX core)
* `u_hdmi_control/m_axi_arvalid[10] ↔ u_hdmi_tx_ctl_merge/m_axi_arvalid[1]` (M10 = VTC)
* `u_hdmi_control/m_axi_araddr[322:328]` (M10 field bits [8:2]) → merge
* `u_hdmi_tx_ctl_merge/txss_ctl_araddr[8:2] + [16]` → `u_hdmi_tx_ss/S_AXI_CPU_IN_araddr`
  — bit 16 **is** driven now (in `26111601` only the read path carried it)
* inside the subsystem: `S_AXI_CPU_IN_araddr[8] → inst/axi_crossbar/m_axi_araddr[25]`
  (M01 field bit 8) and `v_tc/s_axi_araddr[8]` on the same net; `v_tc` `s_axi_arvalid`,
  `s_axi_arready`, `s_axi_rresp` all wired to the inner crossbar.

Both address maps are exactly as configured (checked against
`axi_crossbar_hdmi.xci`: `M02_A00 = 0xB0020000/16`, `M10_A00 = 0xB0030000/16`, and
`v_hdmi_tx_ss_rgb.hwh`: inner `axi_crossbar` `C_AXI_ADDR_WIDTH=17`,
`M00 = 0x0000/16`, `M01 = 0x10000/16`, read+write connectivity all-1, `C_M_AXI_SECURE=0`).
No window overlaps. `R_REGISTER=1`, `S_AXI_SINGLE_THREAD=1`.

So `26111601` (one 17-bit slice, read bit16 connected per §previous) and `26111602`
(bit16 generated in fabric) fail *identically*. Two different ways of carrying address
bit 16 producing the same immediate refusal means **the slicing is not the failing
level**; the refusal comes from the `v_hdmi_tx_ss` control port or from `v_tc` itself.

### 8.4 Blocking write-probe incident — new hard rule

`build/ddc-vtc-26111701/card-vtc-write.sh` was intended to distinguish "no route" from
"slave refused" by *writing* a read-only register. The transaction printed the control
line and then lost the transport:

* the card's debug exec reported `Debug transport lost/timed out; command outcome may be
  unknown. NOT retried.` — the ambiguous action was **not** retried;
* host `sc7f0ctl status` then showed `ready=1` with **`card_beat` frozen** at 14538671
  across three reads (PS heartbeat stopped) and `card_epoch` unchanged;
* the sanctioned recovery `qpcie_upgrade --reboot` (PS warm reset + PCIe rescan, host not
  rebooted) brought the driver back once (`88016` telemetry `status=0x00000003,
  res=3840x2160`) but BAR0 afterwards reads all-ones:
  `Hardware Magic : 0xFFFFFFFF [INVALID]`, and the debug mailbox answers
  `Unsupported debug ABI/magic`. Config space is still visible
  (`lspci -d 12ab:` lists `03:00.0`), so the endpoint links but does not answer memory
  requests. **The card now needs a chassis power cycle** — a warm reset is no longer
  sufficient, and nothing eMMC-resident was touched.

The last `devmem` action issued was a **write to `0xB00B0000`, an HPM1 address that no PL
decoder covers**. Rule going forward:

> **Never write-probe an unrouted HPM1 aperture.** Reads there are answered with a
> decoder error and are safe (`rc=135`, bus keeps working). A *write* there stopped the PS
> heartbeat and cost a power cycle. Use reads, or write only inside a window whose slave
> is known to decode it.

Consequence for the plan: the "write to VTC ID register, see if it ACKs" experiment is
withdrawn. The VTC reachability question must be settled from netlist + simulation + the
driver's own behaviour, not from another MMIO write probe.

### 8.5 What `26111701` therefore has to carry

1. **No DDC change of any kind** (§8.1). Keep the TX SS internal DDC and the pads.
   Keep clearing-state hygiene: `printf reset > .../edid_override` is the only correct
   way to drop an override, and a stale override silently fakes a 256-byte EDID.
2. **VTC**: the address map is not the failing level (§8.2, §8.3). Before rebuilding the
   control path again, settle whether `v_hdmi_tx_ss/S_AXI_CPU_IN` itself refuses the
   `+0x10000` window — gate-level simulation of the deployed `axi_crossbar_hdmi`
   netlist + `sc7f0_axil_merge_2to1` + a `S_AXI_CPU_IN` model decoded exactly like
   `v_hdmi_tx_ss_rgb.hwh`, plus a read of the driver's VTC usage (does
   `XV_HdmiTxSs`/`XVtc` *read* VTC registers during a modeset? if it did, every modeset
   would have taken a synchronous external abort in-kernel, and it has not).
3. `sc7f0_dmabuf_loop` / alpha-blend / host C2H RGB888 acceptance items are unaffected.

## 9. VTC `0xB0030000` root cause: the VTC is clocked by the TX video clock, and Xilinx
###     refuses to read it for exactly that reason — no fabric change is required

Two gate-level runs of the **deployed** netlists
(`scripts/sim_sc7f0_hdmi_xbar_addr_map.sh
/mnt/data-root/.../rgb-a1b1-26111602-20261116T141240Z all`, transcript
`build/ddc-vtc-26111701/sim-xbar/*.rsp`) settle the addressing question:

```
outer  axi_crossbar_hdmi (deployed netlist)
  b0020000 | OKAY | M02 | b0020000        b0030000 | OKAY  | M10 | b0030000
  b002fffc | OKAY | M02 | b002fffc        b0030100 | OKAY  | M10 | b0030100
  b003fffc | OKAY | M10 | b003fffc        b0040000 | OKAY  | M03 | b0040000
  write 0xB0030004 -> M10 addr=b0030004 bresp=0     b00b0000 | DECERR | none
  SC7F0_XBAR_MAP_OUTER_PASS

inner  bd_d638_axi_crossbar_0 (inside v_hdmi_tx_ss_rgb, deployed netlist)
  0ffff | OKAY | M00 | 0ffff        10000 | OKAY | M01 | 10000   <-- VTC window
  10150 | OKAY | M01 | 10150        1fffc | OKAY | M01 | 1fffc
```

So the address bit-16 question is closed on every level that software can reach:
outer crossbar routes `0xB0030000` to M10 with the full address on both read and
write, the fabric merge carries bit 16, and the subsystem's own crossbar routes
`+0x10000` to `v_tc`. **The abort was never an addressing defect**, which is why
`26111601` (one 17-bit slice) and `26111602` (fabric merge) failed identically —
two different ways of carrying bit 16, the same refusal.

The answer is in Xilinx's own TX SS driver,
`build/hdmi-mod-src/xv_hdmitxss.c:2408 XV_HdmiTxSs_ReportSubcoreVersion()`:

```c
if (InstancePtr->VtcPtr){
     if (InstancePtr->IsStreamUp == TRUE){
       Data = XVtc_GetVersion(InstancePtr->VtcPtr);
       ...
     } else {
       xil_printf("  VTC version is not available for reading as ");
       xil_printf("HDMI TX Video Clock is not ready.\r\n");
     }
}
```

Xilinx will not read the VTC unless the HDMI TX **video clock** is running
(`IsStreamUp` is set TRUE only from the TX-core stream-up interrupt,
`xv_hdmitxss.c:1275`). That clock in this design is:

* `v_hdmi_tx_ss_rgb.hwh`: `v_tc/clk` shares the net with `v_hdmi_tx/video_clk`;
* `rtl/zu4ev_pcie_card_top.v`: the subsystem's video clock pin is
  `.video_clk(phy_tx_video_clk)` / `.s_axis_video_aclk(phy_tx_video_clk)`;
* `phy_tx_video_clk` is the VPHY TX video clock — 0 Hz until the TX PLL is
  programmed by a commit that reaches the PHY.

Everything then lines up without inventing a fabric defect:

| observation | explanation |
|---|---|
| reads at `0xB0030000` abort **immediately** (§8.2) | the VTC read-return path is in the video-clock domain; with that clock at 0 Hz the access is answered with an error response rather than hanging. Xilinx documents the read as "not available" in exactly this state |
| the kernel never oopsed although `XV_HdmiTxSs_Reset()` pokes the VTC at probe (`xv_hdmitxss.c:833-853`) | those are **writes**; a posted write has no read-return dependency |
| the driver survives a modeset but no picture appears | writes issued while the video clock is off cannot be trusted to latch; the VTC keeps its reset timing, so the TX never produces valid timing and the stream never comes up |
| `0xB00B0000` and `0xB0030000` cost the same | both are error responses; cost alone cannot separate a decoder DECERR from a slave error response (and the write probe that could has been withdrawn, §8.4) |
| `26111601` "VTC unreachable" | same clock state, so the same refusal — the 17-bit-slice theory was never the cause |

**Consequences for `26111701`:**

1. **No address-map, merge or crossbar change.** `sc7f0_axil_merge_2to1` and the two
   64 KiB slices stay: they are proven correct in simulation of the deployed netlists.
   Do not spend another build on the bit-16 theory.
2. The VTC question becomes a **sequencing** question, and it is testable from the
   existing fabric: the `sc7f0_probe` clock monitor already reports
   `tx_video_clk` (`0xA00006B4`). Bring-up order to verify on hardware is
   mode (EDID §8.1) → VPHY PLL programmed → `tx_video_clk` non-zero →
   `XV_HdmiTxSs_StartStream()` VTC writes → stream-up. If `tx_video_clk` is still
   0 after a commit, the blocker is the VPHY/clock path, not the VTC.
3. Any VTC readback added to scripts must be gated on that clock being non-zero, for
   the same reason the Xilinx driver gates it on `IsStreamUp`. Reading
   `0xB0030000` before the link is up is expected to abort and must not be treated as
   a bus bug.
4. Re-verify the DRM TX path on the **already-programmed** `26111602` first
   (`scripts/verify_sc7f0_hdmi_tx_drm.sh --mode 3840x2160-60`) now that EDID reads for
   real (§8.1). The earlier `flip_done timed out` evidence predates the EDID fix and
   was taken with no mode at all, so it does not prove the commit path is broken.
