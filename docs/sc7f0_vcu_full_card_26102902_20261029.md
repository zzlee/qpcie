# SC7F0 Phase 1 / Todo 1.3 — encoder-only VCU in the whole card (synthesis, implementation, bitstream, XSA)

Date: 2026-10-29. Scope: full-card build with the encoder-only VCU enabled —
project creation, synthesis, `opt_design`/`place_design`/`phys_opt_design`/
`route_design`, bitstream, `hardware.xsa` export and the timing/CDC/personality/
Gray gates. No PetaLinux, device tree, driver, packaging, flashing or on-card
work was performed. No pre-existing build directory was modified or overwritten;
the frozen R7 tree `build/dual-video-26102901-r7` is untouched and is the
baseline of every delta in this document.

**Authoritative build: `build/dual-video-26102902-vcu-r5`** — `C_VERSION =
32'h26102902`, VCU enabled (`xbar` memory interconnect), wrapper exit code **0**,
`hardware.ok` written. Gate verdict: **`VCU_DELTA_PASS`**
(`build/vcu-delta-review-26102902-r5/review.json`).

## 1. Script changes

| file | change | behaviour with the switch off (default) |
| --- | --- | --- |
| `scripts/build_zu4ev.tcl` | new `SC7F0_ENABLE_VCU` (`0/1/true/false/yes/no`, anything else is a hard error). Enabled: `create_zu4ev_ps_bd [expr {!$debug_profile}] 1 "xbar"`. Unset/0: the original `create_zu4ev_ps_bd [expr {!$debug_profile}]` call, unchanged. A VCU request together with `SC7F0_PROFILE=debug` is rejected (the debug profile has no `dp_mem_clk`). VCU builds default their XSA name to `hw_platform/sc7f0_hdmi_vcu.xsa`. | byte-identical behaviour |
| `scripts/impl_sc7f0_dual_video.tcl` | same switch, plus: BD must contain `vcu_0`, `xbar_vcu_enc`, `dwc_vcu_mcu`, must contain **no** `smartconnect` cell, and must map exactly one `SEG_vcu_0_Reg` at `0x8008_0000` (`SC7F0_VCU_BD_OK`); the C2H personality audit additionally requires exactly one VCU hard macro and no `smc_vcu*` cell; after route the hard macro and the video-merge path are re-proved (`SC7F0_VCU_ROUTED_CELL`) and the routed Gray re-check is delimited by `SC7F0_GRAY_ROUTED_BEGIN/END`; `SC7F0_TIMING_GATE=record` writes the shipped whole-design gate verdict to `timing-gate-record.json` instead of aborting before the XSA; `SC7F0_IMPL_RESUME=postroute` re-runs only the routed reports/gates/XSA on an existing run | unchanged (`strict` gate, no resume) |
| `scripts/build_sc7f0_dual_video_hw.sh` | forwards `SC7F0_VERSION`, `SC7F0_ENABLE_VCU`, `SC7F0_TIMING_GATE` (defaults `26102901`, `0`, `strict` — the frozen R7 values), records them in `environment.txt`, adds the two VCU scripts to the source manifest, and writes a `hardware.ok` that states which gate mode produced the build | unchanged with the defaults |
| `scripts/check_sc7f0_vcu_delta.py` | **new** scoped whole-card delta gate (§5). Re-reads the reports, never the logs. Fail-closed (`refusing to overwrite` on an existing output dir, absolute margins + every delta class). In VCU mode it additionally requires the VCU hard macro, the `pl_clk1` reference period, the routed Gray evidence and the VCU markers, and it reports any clock the revision introduces. Self-tested with R7 as candidate *and* baseline: the zero-delta case must PASS | n/a |
| `scripts/report_sc7f0_vcu_numbers.py` | **new**, read-only extraction of the report numbers used below | n/a |

`C_VERSION` went to `26102902` because `AGENTS.md` makes a version bump
mandatory whenever BD/IP changes, and a distinct ID is what lets software tell a
VCU bitstream from the frozen R7 card. R7 keeps `26102901`.

## 2. Commands

```bash
source /opt/Xilinx/Vivado/2023.2/settings64.sh
export XILINXD_LICENSE_FILE=2101@192.168.200.112
SC7F0_ENABLE_VCU=1 SC7F0_VERSION=26102902 SC7F0_TIMING_GATE=record \
  bash scripts/build_sc7f0_dual_video_hw.sh build/dual-video-26102902-vcu-r5

python3 scripts/check_sc7f0_vcu_delta.py \
  --candidate build/dual-video-26102902-vcu-r5 \
  --baseline  build/dual-video-26102901-r7 \
  --console   build/dual-video-26102902-vcu-r5-logs/impl-console.log \
  --baseline-gate <R7 timing-gate record> \
  --out build/vcu-delta-review-26102902-r5 --vcu 1        # -> VCU_DELTA_PASS
```

`SC7F0_TIMING_GATE=record` is **not** a waiver of the shipped absolute gate
(`scripts/check_sc7f0_timing.py`). That gate fails closed on the frozen R7
inventory as well (its R7 record is stored as
`build/vcu-delta-review-26102902-r5/r7-baseline-gate.json`: 2,660 unreviewed
vendor/XPM FIFO CE + LUTRAM crossings, `CDC-10 Critical=29`,
`CDC-12 Critical=10`, `TIMING-9`, `TIMING-18`, 7 input / 6 output ports without
delays — see `docs/sc7f0_full_profile_r6_review.md`). A build that changes only
"what the VCU added" can therefore only be judged as a delta, which is what §5
does; the absolute verdict of the shipped gate is still recorded verbatim in
`<build>/timing-gate-record.json` and quoted in §5.

The frozen baseline behaves exactly as designed in `strict` mode: R7's own
implementation console ends with `Dual-video timing/CDC gate failed; XSA
withheld`, so `build/dual-video-26102901-r7/` contains **no** `hardware.xsa`
and no gate record, and R7's XSA was produced afterwards by the separate
reviewed export (`scripts/export_sc7f0_reviewed_r7.tcl` →
`build/r7-reviewed-acceptance.1793238509/hardware.xsa`, 3,906,802 bytes,
SHA-256 `91f71cb8…aac82d`). `record` + scoped review follows that same
precedent — export only under a named review — but does it inside one flow and
with the review committed to a machine-readable file.

Two things worth reading carefully. The design's critical path *moved*: in R7 it
was `clk_pl_0` at +0.923 ns, here `clk_pl_0` **improves to +1.911 ns** and the
worst path in the card is the PCIe GT-derived 250 MHz group
(`pcie4_uscale_plus_0_gt_top_i_n_43`, 4,305 endpoints, +1.052 ns); the
`pcie_user_clk` / `pipe_clk` margin loss is placement pressure around the VCU
hard macro, not changed PCIe logic — every clock still ends with positive WNS
and WHS and zero TNS/THS. And `clk_pl_1`, which does not exist at all in a
VCU-off build, is present, constrained and met: 30.002 ns / 33.331 MHz
(`PL1_REF_CTRL @ 0XFF5E00C4` with `CLKACT=0x1, DIVISOR0=0x2d, DIVISOR1=0x1,
SRCSEL=0x2` in the exported `psu_init.c`), i.e. **+0.0067 % period** against the
30.000 ns / 33.333333 MHz nominal — the RPLL integer-divider quantisation, not a
VCU problem.
