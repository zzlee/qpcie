## 3. 缺陷一：DT 寬度（已修復）

`vid_phy_controller_rgb` 是在 `rtl/zu4ev_pcie_card_top.v` 裡實例化，不在 PS block design，
所以 device-tree generator 對 `phy@b0000000` 沒有任何 HWH 來源；該節點每個 `xlnx,*` 都是手寫，
legacy 4PPC 值由 `sc7f0-hdmi-rx.dtsi` 提供、`sc7f0-rgb-compositor.dtsi` 覆蓋。這正是「已出貨影像
描述了一個 fabric 沒有的資料路徑」的來源，而且不是裝飾：

| 程式碼位置（hdmi-modules 82209b0） | 行為 |
|---|---|
| `hdmi/phy-vphy.c:408/504` | `xlnx,input-pixels-per-clock → XVphy_Config.Ppc`；`xlnx,transceiver-width → XVphy_Config.TransceiverWidth` |
| `xvphy_hdmi.c:1838-1848` | `TransceiverWidth==2 || GTPE2 → RxDataWidth 20 / RxIntDataWidth 2`，否則 `40 / 4` |
| `xvphy_gthe4.c:602-617` | 兩者經 DRP 寫入 GTHE4 `RX_DATA_WIDTH`（0x03[8:5]）與 `RX_INT_DATAWIDTH`（0x66[1:0]） |
| `xvphy_hdmi.c:1170-1320` | `Ppc` 決定 RX MMCM `Mult` 取整與 `Clk0/1Div` 選擇（即 fabric 拿到的 user/video clock） |

4/4 树在 GT 已鎖定的條件下的實測（前一視窗，PL 同一 bit）：`PLL_LOCK=0x7`、`RX_INIT_STATUS=0x00070707`、
`CLKDET_FREQ_RX=148,467,456`、RXSS `PIO_IN=0x187`（cable+GTLNKRDY+VID_RDY+SCDC），但
`RX_TDLOCK(0xB000010C)=0`、`0xB00101D4` 錯誤計數器饱和 `0xFFFF`、VTD 完全無時序——字元到了，fabric 讀不了。

新增兩道閘（不再靠卡去發現）：

- `scripts/audit_sc7f0_rgb_compositor_image.sh`：對**建置產出的 DTB** 檢查 `phy@b0000000`
  （`transceiver-width`、`input-pixels-per-clock`、`transceiver-type`、`nidru`、通道數、IRQ）與
  RX/TX 的 `input-pixels-per-clock`/`max-bits-per-component`，並要求寬度與 PPC 一致。
  實測：**FAIL r1、FAIL r3、PASS r2、PASS r4**。
- `scripts/check_sc7f0_hdmi_dt.py --rgb`：編譯整板 DTS 並與 `*_rgb` XCI 逐欄核對
  （`SC7F0_CAPTURE_DT_PASS` / `SC7F0_RGB_GEOMETRY_DT_PASS` / `HDMI_DT_PASS`；故意把覆蓋值改回 4 會如期 FAIL）。

## 4. 缺陷二：GT 參考時脈（未修復，第一因）

同一次開機、同一組暫存器、以「硬體對硬體」方式量到：

| 量測 | 值 | 意義 |
|---|---|---|
| PL clock probe `0xA0000680` | `0x26102201` | probe 存在於此 bitstream |
| PL clock probe `0xA0000684 RX_CLK_FREQ_HZ` | **593,948,427 Hz** | IT6663 在接頭上看到的 TMDS 時脈＝4K60 訊號確實存在 |
| PL clock probe `0xA0000688 DRU_CLK_FREQ_HZ` | 156,234,866 Hz | 板振盪器 |
| VPHY `0xB000021C CLKDET_FREQ_DRU` | 156,237,824 Hz | 與 probe 差 0.002 % → **偵測器刻度可信** |
| VPHY `0xB0000210 CLKDET_FREQ_RX` | **57,081,856 Hz** | GT 參考輸入實際看到的時脈 |
| 比例 | **10.41（需 4.00）** | 1/40 分支需要 char/4 = 148.49 MHz |
| VPHY `0xB0000018 PLL_LOCK` | `0x00000000` | 沒有任何 RX PLL 鎖定 |
| VPHY `0xB0000028 RX_INIT_STATUS` | `0x00040404` | 每通道 0x4（前一視窗為 0x7） |
| RXSS `0xB0010064 PIO_IN` | `0x00000001` | 僅 cable detect |
| `RX_TDLOCK 0xB000010C` | `0x00000000` | 目標條件 |
| host `qpcie` V4L2 | STREAMON 被接受但永不回 buffer（30 s timeout） | 無串流可搬 |

驅動算式（同一份模組原始碼，非推測）：

- `xvphy_hdmi_intr.c:776` `HdmiRxRefClkHz = XVphy_ClkDetGetRefClkFreqHz(RX)`（就是 `0x210` 的值，四捨五入到 10 kHz）
- `xvphy_hdmi.c:1818` 只有 `refclk >= XVPHY_HDMI_GTHE4_CPLL_REFCLK_MIN (50 MHz)` 才走 CPLL 分支
  （57.08 MHz ≥ 50 MHz，故走 CPLL，不是 DRU 分支）
- `xvphy_hdmi.c:1822` 串流為 1/40（IT6663 回報 `scrambled=1`、`scdt_lock=1`）→ `lineRate = refclk × 40`
  → **2.283 Gb/s**，而實際串流為 **5.939 Gb/s**（0.384×）→ CPLL 不可能鎖定 → GTLNKRDY/VID_RDY 不成立 → `TDLOCK` 恆 0

前一視窗 `0x210 = 148.467 MHz = char/4`，同一算式得到 5.94 Gb/s，CPLL 如設計鎖定（然後卡在缺陷一）。
也就是說：**兩個缺陷必須同時成立才會鎖上**；本輪修掉了 DT 那一半，另一半在 IT6663 TX-port 輸出時脈比例
（MCU 設定），不是 RTL／IP／DTSI／驅動可控。本輪**未**對 IT6663 做任何寫入，也未重啟/更新 MCU。

`xlnx,rx-refclk-sel = <1>`（IP `C_RX_REFCLK_SEL {1}`）與暫存器 `0xB0000010 = 0xC8000121`（bits[7:4]=0x2，
`test_app/sc7f0_hdmi_init.c` 註解所稱 GTREFCLK1）一致，故「選到錯誤 refclk 腳位」已排除。
