## 5. The one thing this release is not: a matched 0x26102902 PS image

No PetaLinux build exists for the VCU handoff. `petalinux/qpcie-zu4ev/project-spec/hw-description/system.xsa`
is still the R7 XSA `91f71cb8…c82d`, so the only `image.ub` in the tree carries
`PL_BASE_VERSION=0x26102901`. Consequences, all verified offline:

* `psu_init.c` of the candidate programs `CRL_APB_PL1_REF_CTRL @ 0xFF5E00C4 =
  0x01012D02` (pl_clk1 = 33.331 MHz, the VCU `pll_ref_clk`); the R7 `psu_init.c`
  behind the shipped FSBL has **no such write** → the VCU would be unclocked;
* the shipped DT has no DTGen `vcu`/`al5e` register node; `project-spec/.../vcu.dtsi`
  is the pre-existing fixed-clock placeholder that
  `docs/sc7f0_vcu_daemon_plan.md` §41 explicitly calls "NOT integrated VCU hardware";
* **the capture path is unaffected**: `scripts/check_sc7f0_vcu_address_map.py`
  shows every R7 address window byte-identical (HP0/HP1 windows, HPM0_FPD
  `0xA000_0000`, HPM1_FPD `0xB000_0000`), with only additions
  (`vcu_0` Reg `0x8008_0000…0x8017_FFFF` on HPM0_LPD, plus VCU HP2/HP3 DDR masters),
  and the card's existing interrupt set keeps its `pl_ps_irq0[4:0]` bit numbering.

Therefore `PS_IMAGE_MATCH.json` records `deployable: false` with the reason,
`NOT_DEPLOYABLE` is present, and `release.json` carries
`ps_image_pl_base_version: 0x26102901` + `not_deployable_reason`. Packaging is
accepted (`package.ok`); **commitment to a card is blocked by design**, and the
blockers are enforced by the deploy tool, not by prose:

1. `NOT_DEPLOYABLE` present → refusal before any SSH session;
2. `release.json` / `PS_IMAGE_MATCH.json` `deployable != true` → refusal;
3. `imported-xsa.sha256` of `SC7F0_PS_BUILD_DIR` must equal the SHA-256 of this
   release's `fpga/hardware.xsa` → refusal naming "PS image was built from a
   different hardware XSA" (proved reachable in `logs/final-verify.log`).
